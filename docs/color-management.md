# Colour management

FlashRaw develops RAW data to **linear sRGB** by default and encodes the display outputs with
the sRGB curve. Three layers build on that, all optional and all free when unused:

1. **Output colour spaces**: Display P3, Adobe RGB (1998), ProPhoto RGB and Rec. 2020, selected
   with one option. Built in, no extra dependency, no cost per pixel.
2. **Tagging**: a standard ICC profile for each space is generated by the library
   (`ColorSpace::icc_profile`) and returned with every RGB frame, ready to embed in files.
3. **Arbitrary ICC profiles** (cargo feature `icc`): convert to any RGB output profile, with
   rendering intent and black point compensation.

Raw outputs (`raw-u16`, `raw-f32`, `normalized`) are sensor data and have no colour space; the
options are ignored for them and the frame reports `srgb` with no profile.

## Output colour spaces

| Space | Name(s) accepted | Primaries | White | Transfer curve of the display outputs |
|---|---|---|---|---|
| sRGB (default) | `srgb` | Rec. 709 | D65 | piecewise sRGB (IEC 61966-2-1) |
| Display P3 | `display-p3`, `p3` | DCI-P3 | D65 | sRGB curve |
| Adobe RGB (1998) | `adobe-rgb`, `adobergb` | wide greens | D65 | pure gamma 563/256 (2.199...) |
| ProPhoto RGB | `prophoto`, `romm` | very wide | D50 | gamma 1.8, linear toe (slope 16 below 1/512) |
| Rec. 2020 | `rec2020`, `bt2020` | BT.2020 | D65 | BT.709/BT.2020 OETF with the 12-bit constants (4.5 L below 0.018053968..., else 1.09929682... L^0.45 - 0.09929682...) |

The linear outputs (`linear-rgb`, `linear-rgb16`, `linear-rgb-f16`) carry the primaries of the
space with a linear transfer function. The display outputs (`rgba8`, `rgb16`) additionally
apply the curve in the table. Values outside the gamut of the space are not clipped by the
float output; the integer outputs clip to `[0, 1]` after the matrix, like sRGB does.

### How it works

The develop pass multiplies camera RGB by one 3x3 matrix (`cam_to_rgb`, and `cam4_to_rgb`
for four-colour sensors). An output space is one more 3x3 matrix, linear sRGB to the space,
that is **multiplied into the camera matrix once per decode**: the per-pixel work is the same
as for sRGB. The matrices are derived from the primaries and white points of the table and
are Bradford-adapted to the D50 connection space of ICC profiles, exactly like the profiles
that describe them, so a file tagged with `icc_profile()` is displayed as intended. White maps
to white in every space.

The display encoders use one lookup table per space: 8-bit output indexes a 16384-segment
table (sRGB and Display P3 keep their original 4096-segment sRGB table, so their output is
bit-identical to a build without colour spaces), 16-bit output interpolates a 16384-segment
table. Pure power curves are steep at zero, so Adobe RGB output below roughly 6e-5 linear
(more than 13 stops under white) is quantised to at most 3 codes of 8 bits; the sRGB-like
curves have a linear toe and do not have this limit.

Every backend honours the option identically: scalar and SIMD CPU code, region and tile
decodes, the DNG opcode (staged) path, staggered (Super CCD) sensors, and the GPU compute
shaders (the matrix is folded into the uniform camera matrix, the curve tables are uploaded
like the sRGB ones; GPU and CPU results agree within the existing tolerances).

## Tagging

`ColorSpace::icc_profile()` writes a small ICC v4 matrix/TRC display profile for the space
("FlashRaw Display P3", ...) and `icc_profile_linear()` the same primaries with a linear curve
for the linear outputs. They are generated by code (about 600 bytes each, reproducible, no
binary blobs). `RawFrame::icc_profile()` returns the right one for the frame's output: a
display profile for `rgba8` / `rgb16`, a linear one for the linear outputs, the profile that
was used for an output profile, and `None` for raw outputs and for frames made from the
embedded preview (`preview_fallback`, always reported as sRGB).

The CLI embeds the profile in the files it writes:

| Format | Where |
|---|---|
| TIFF (`.tif`) | ICCProfile tag 34675 |
| JPEG (`.jpg`) | APP2 `ICC_PROFILE` chunk(s) |
| Netpbm (`.ppm`, `.pgm`) and `.raw` | no profile support in the format |

The CLI's preview extraction (`flashraw preview`, `thumbnail`) writes the camera's embedded
JPEG bytes untouched and is not affected.

## ICC output profiles (feature `icc`)

With the `icc` cargo feature (on by default everywhere: the library, the CLI, the C library, the
Python wheels and the WASM builds; see [building.md](building.md) to leave it out), `DecodeOptions::output_profile` converts RGB outputs to any
RGB ICC profile (v2 or v4):

```rust
use flashraw::{DecodeOptions, OutputFormat, OutputProfile, RenderingIntent};

let icc = std::fs::read("printer.icc")?;
let opts = DecodeOptions {
    output: OutputFormat::Rgb16,
    output_profile: Some(
        OutputProfile::new(icc)
            .with_intent(RenderingIntent::RelativeColorimetric)
            .with_black_point_compensation(true),
    ),
    ..Default::default()
};
```

The frame reports `ColorSpace::Custom` and `icc_profile()` returns the profile. A profile that
is malformed, not an RGB output/display/colour-space profile, or unusable returns
`Error::InvalidArgument` (never a panic); without the feature the error says "built without ICC
support" (`flashraw::icc_supported()` tells which build you have).

There are two paths, chosen automatically:

* **Matrix/TRC profiles** (most display and working-space profiles, including everything
  `icc_profile()` writes): the colorant matrix is folded into the camera matrix and the profile's
  tone curves become encoder tables, in the same single pass as a built-in space. The rendering
  intent has no effect (a matrix profile converts the same way for every intent) and neither
  does black point compensation (its black is zero). Profiles with three different curves get
  one table per channel. These work for the linear outputs too: the matrix is applied and the
  curve is not, and the frame carries a linear-curve profile with the same primaries.
* **Profiles with lookup tables** (A2B/B2A: printers, scanners, many camera profiles): the image
  is developed to linear ProPhoto RGB (wide, so camera colours clip as little as possible),
  converted by a second parallel pass over the whole image in `f32`, and then quantised and
  oriented. **This is slower** (it needs a float copy of the image and a table interpolation per
  pixel; on a 24 MP file the second pass costs roughly as much as the rest of the decode) and it
  only applies to the display outputs (`rgba8`, `rgb16`): the linear outputs have no device
  encoding and fail with `InvalidArgument`. The intent selects the table; black point
  compensation maps the image black to the black of the profile (computed in linear light from
  the profile's own conversion of device black), and is a no-op for profiles with a zero black.

GPU decodes (`Backend::Gpu`, or `Auto` choosing the GPU) fall back to the CPU for output
profiles, like they do for DNG opcode lists that change the output; GPU-resident outputs
(`gpu-rgba8`, ...) support the built-in spaces only and return `InvalidArgument` for a profile.
The colour conversion is done by a pure-Rust colour management engine (licensed
BSD-3-Clause OR Apache-2.0, no C dependencies; it is only built with the `icc` feature). It treats `f32` data as 14-bit, which is
below the 16-bit output precision; the second pass agrees with the folded pass to a few codes
of 16 bits.

Input (camera) profiles are not supported: FlashRaw develops with the colour matrices of the
file or its camera database, and DNG camera profiles (HueSatMap, LookTable) are reported in the
metadata but not applied.

### WebAssembly

The WASM builds include the `icc` feature (about 86 KiB more brotli-compressed than a build
without it, on top of about 8 KiB for the built-in spaces). Pass the profile bytes as
`outputProfile` (a `Uint8Array`); it is base64-encoded into the options of the call and
validated in WASM, so garbage rejects with `InvalidArgumentError`. A profile cannot panic the
parser in a way a browser could recover from (the WASM build aborts on panic), which is why the
parser is fuzzed (see below).

## API summary

| Where | Select a space | ICC profile | Output profile |
|---|---|---|---|
| Rust | `DecodeOptions::color_space: ColorSpace` | `ColorSpace::icc_profile()`, `icc_profile_linear()`, `RawFrame::icc_profile()` | `DecodeOptions::output_profile: Option<OutputProfile>` (`OutputProfile::new(bytes).with_intent(..).with_black_point_compensation(..)`), `RenderingIntent` |
| CLI | `--color-space srgb\|display-p3\|adobe-rgb\|prophoto\|rec2020` | embedded in `.tif` and `.jpg` | `--output-profile file.icc --intent perceptual\|relative\|saturation\|absolute --bpc` |
| C | `flashraw_decode_options.color_space` (`FLASHRAW_COLOR_SPACE_*`) | `flashraw_frame_icc_profile()`, `flashraw_icc_profile()`, `flashraw_frame_color_space()` | `output_profile`, `output_profile_len`, `intent`, `black_point_compensation`; `flashraw_icc_supported()` |
| C++ | `decode_options::color_space` | `frame::icc_profile()`, `flashraw::icc_profile(cs, linear)` | `decode_options::output_profile` and friends, `flashraw::icc_supported()` |
| Python | `decode(color_space="display-p3")` | `frame.icc_profile`, `flashraw.icc_profile(space, linear=False)` | `decode(output_profile=bytes_or_path, intent=..., black_point_compensation=...)`, `flashraw.icc_supported()` |
| JavaScript | `decode({ colorSpace: 'display-p3' })` | `frame.iccProfile` (`Uint8Array`) | `decode({ outputProfile, intent, blackPointCompensation })` |

`frame.color_space` / `frame.colorSpace` report the space (`custom` after an output profile).
The compatibility-layer crate keeps its own output-space handling and is not affected.

## Tests and fuzzing

* `crates/flashraw/src/color.rs`: matrices round-trip between every pair of spaces and map white
  to white, match published matrices, curves match reference values and invert exactly, the
  tables follow the curves, written profiles are well formed.
* `crates/flashraw/src/icc.rs` (feature `icc`): the written profiles parse with the colour
  engine, with the right colorants, curves and description; matrix profiles fold into the
  develop pass with the same matrix and curve as the built-in space; truncated, bit-flipped and
  garbage profiles return errors; the second pass agrees with the folded pass.
* `crates/flashraw/tests/color_spaces.rs`: every space, every RGB output, scalar vs SIMD and
  1 vs N threads are bit-identical; linear outputs equal the sRGB outputs times the matrix;
  display outputs apply the curve; region decodes equal the full decode; frames report their
  space and profile.
* `crates/flashraw-cli/tests/color_tagging.rs`: TIFF and JPEG files contain the profile.
* `crates/flashraw-capi`, `crates/flashraw-python`, `npm/tests/color.test.mjs`: the bindings.
* `fuzz/fuzz_targets/icc_profile.rs`: arbitrary bytes as an output profile, all intents.

sRGB output (the default) is bit-identical to releases without colour spaces.
